## Findings requiring repair
1. High: MentorWalletService.wallet and requestPayout compute available = released - reserved, omitting already-paid amounts. Example: released 850,000, paid 850,000 and reserved 0 still displays/accepts 850,000. The Admin decision path does subtract paid and allocate remaining entries, so this is a false balance/reservation bug, not evidence of a completed duplicate bank transfer.
2. High: SepayPaymentService.verifyAuth returns without verification when the configured API key is blank. application.properties also supplies a fixed committed fallback key. Require explicit private configuration and fail closed; replace any key used in a real deployment that was committed.
3. High: webhook transfer type and destination-account validation are conditional on fields being non-null. Missing identity fields can bypass those checks; a missing transaction identifier is replaced by the current time rather than rejected. Require complete payload validation before touching financial records.
4. Medium: webhook lookup is not constrained to gateway SEPAY and settlement only excludes SUCCEEDED, without checking payment status/expiry. Define and test handling of cancelled/expired/late transfers and cross-provider references rather than silently converting them into successful SePay payments.
5. Reporting limitation: Admin gross payments and commission are calculated before refunds and escrow release. They are not cash available, realized fee income or mentor payouts. Wallet rounds fees to whole VND, while Admin aggregate commission rounds to two decimals, which may disagree on small amounts/fractional rates. Keep labels explicit and reconcile reporting with ledger policy before treating it as a cash-flow statement.

## Follow-up validation
Use a disposable SQL Server database with the complete reviewed migrations (through V13), not automatic V8-V13 backfills on existing local data. Add integration scenarios for valid and invalid settlement, repeated/concurrent callbacks, refunds, release after seven days, and payout followed by a second withdrawal request. Reconcile payment amount = remaining held funds + refunded amount + released mentor share + platform fee, and mentor available = released share - paid payouts - active reservations. Payout ledger entries represent an administrator recording an external bank transfer; this implementation does not automatically send money to a mentor.
